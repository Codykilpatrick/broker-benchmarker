Under-Replicated Partitions

CRITICAL

What This Means

One or more partitions have fewer in-sync replicas than their replication factor requires. This means data durability is degraded — if the remaining broker fails, data loss is possible.

Note: In this single-node dev setup, under-replication is expected since replication factor is 1. This alert is most relevant in multi-broker deployments.

Likely Causes

  • A broker node is down or unreachable
  • A follower is lagging too far behind to be in-sync
  • Network partition between broker nodes
  • A broker was restarted and is still catching up

Recommended Actions

  1. Check cluster health: 
    docker exec monitoring-redpanda-1 rpk cluster health
  2. List under-replicated partitions: 
    docker exec monitoring-redpanda-1 rpk topic describe --print-partitions benchmark_64kb_0
  3. Check broker status: 
    docker exec monitoring-redpanda-1 rpk cluster info
  4. If a broker recently restarted, wait for it to catch up — monitor redpanda_kafka_under_replicated_replicas trending back to 0.
  5. If a broker is permanently lost in a 3-node cluster, trigger partition recovery: 
    docker exec monitoring-redpanda-1 rpk cluster partitions move-cancel

Metrics to Watch

  • redpanda_kafka_under_replicated_replicas — count of under-replicated replicas (should be 0)
  • redpanda_cluster_unavailable_partitions — partitions with no leader (more severe)
